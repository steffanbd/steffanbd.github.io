SQL & Access — Reconciliation, Recruiting & Schema Design

SQLMS AccessWorkdayArchibus

Query patterns from graduate SQL coursework, written in the shape of the reconciliation and workforce-reporting problems described in Experience — plus the relational model those queries actually sit on top of.

Schema — building → room ↔ department
Rooms shared across more than one department
Many-to-many resolved through the junction table
SELECT r.room_id, b.name AS building,
       COUNT(rda.dept_code) AS depts_sharing_room
FROM rooms r
JOIN buildings b ON b.building_id = r.building_id
JOIN room_dept_assignments rda ON rda.room_id = r.room_id
GROUP BY r.room_id, b.name
HAVING COUNT(rda.dept_code) > 1
ORDER BY depts_sharing_room DESC;
Flag space records out of sync between systems
Archibus vs. Workday department reconciliation
SELECT a.room_id, a.dept_code AS archibus_dept,
       w.dept_code AS workday_dept, a.last_updated
FROM archibus_space a
JOIN workday_org w ON a.cost_center = w.cost_center
WHERE a.dept_code <> w.dept_code
  AND a.last_updated >= '2026-01-01'
ORDER BY a.last_updated DESC;
Recruiting funnel conversion by stage
Workforce & recruitment metrics reporting
-- conversion rate, stage-over-stage
SELECT stage,
       COUNT(*) AS candidates,
       ROUND(COUNT(*) * 100.0
         / LAG(COUNT(*)) OVER (
             ORDER BY stage_order
           ), 1) AS pct_of_prior
FROM ats_candidates
WHERE req_open_date >= '2026-04-01'
GROUP BY stage, stage_order
ORDER BY stage_order;
Same relationships, drawn in Access. This is the schema Archibus's own space-and-department data follows: a building owns many rooms — a plain one-to-many, one foreign key. A room and a department don't own each other outright, though — a shared conference room serves more than one department, and a department spans more than one room — so that's a many-to-many, and neither Access nor SQL can express it with a single foreign key. room_dept_assignments resolves it: a junction table with a composite key, dragged into Access's Relationships window with referential integrity enforced on both foreign keys, so a room can't be assigned to a department that doesn't exist and a building can't be deleted out from under its rooms.

Predictive Model — Feature Importance

RXGBoostOLS Regressionggplot2

From graduate Predictive Analytics coursework — an XGBoost model built in R for a team real-estate pricing project, alongside an OLS baseline. Reconstruction of the feature-importance output below, plus the R this ran on.

R — OLS baseline, then the XGBoost fit behind the chart above
Baseline — interpretable coefficients
lm(), for the number a stakeholder can be walked through
library(tidyverse)

ols <- lm(sale_price ~ sqft + neighborhood_score +
             year_built + bedrooms + lot_size + school_rating,
           data = listings)

summary(ols)
#> sqft                  142.30    9.81   14.51  <0.0001
#> neighborhood_score  8420.00 1205.00    6.99  <0.0001
#> year_built            611.40  140.20    4.36  <0.0001
#> Adjusted R-squared: 0.71
XGBoost — non-linear fit, then the chart itself
xgboost() + xgb.importance() → ggplot2
library(xgboost); library(ggplot2)

fit <- xgboost(data = train_x, label = train_y,
    nrounds = 200, max_depth = 4, eta = 0.05,
    objective = "reg:squarederror", verbose = 0)

imp <- xgb.importance(model = fit)

ggplot(imp, aes(reorder(Feature, Gain), Gain)) +
  geom_col(fill = "#0E6E58") + coord_flip() +
  labs(title = "Feature Importance — Gain", x = NULL)
Why run both. XGBoost catches interactions an OLS baseline can't — lot size matters more once school rating is already high — but the OLS summary is what actually explains a coefficient to a stakeholder who asks "why." Running both as a script rather than a notebook of manual steps means the same pipeline reruns cleanly on next semester's listings, and ggplot2 turns whichever model wins into the chart above without leaving R.
